# 个人管家新版任务看板设计说明

本稿整理本轮 grill-me 访谈的决定，服务于「从事项进入 Codex 执行，并持续掌握进展」的目标。五栏看板是基础，大卡承载长期项目，小卡承载可执行的子任务，资料与总结围绕项目沉淀。

日期：2026-10-02。当前安装版本仍为 0.1.0，本稿描述下一版需求，未表示新版界面或聊天联动已经实现。原始参考资料为 `D:\Desktop\功能设计清单.md`；本轮用户的明确选择优先于原清单中的界面与发布设想。

## 设计层级

| 层级 | 作用 | 本轮决定 |
| --- | --- | --- |
| 看板基础 | 表示工作所处阶段 | 灵感池 → 待启动 → 进行中 → 待验收 → 已结项 |
| 任务对象 | 组织目标和工作 | 大卡是长期项目，小卡是所属子任务；两者共用五阶段 |
| 执行关联 | 将事项交给 Codex 并跟进 | 每张小卡关联一个主聊天，跨阶段沿用，可附加其他聊天 |
| 项目资料 | 保存成果、决定与回顾 | 在项目内集中提供资料、引用问答与阶段回顾 |
| 本地保存 | 保持状态、关联与资料可恢复 | 沿用本地存储和备份，聊天关联保存真实引用 |

阶段表示工作进度，执行状态表示当前是否运行、等用户处理或失败。执行状态显示在卡片上，不增加第六栏。

## Dashboard 与大小卡

左侧「个人管家」入口打开 Dashboard。首页就是一张五栏看板，所有项目大卡按各自阶段排列。展开一个项目时，它的小卡按各自阶段出现在这张看板的对应栏中；大卡仍留在自己的阶段栏，其他项目大卡继续可见。

一次只展开一个项目。展开另一个项目时收起前一个项目的小卡。每个项目通常不超过 10 张小卡，展开后直接显示全部，无需分页；这个数量是预期规模，不是创建上限。

例如，项目 A 展开后可以呈现如下结构：

| 灵感池 | 待启动 | 进行中 | 待验收 | 已结项 |
| --- | --- | --- | --- | --- |
| A · 后续想法（小卡） | A · 数据整理（小卡） | 项目 A · 1/5（大卡） | A · 导入功能（小卡） | A · 基础框架（小卡） |
| 其他项目的大卡 | 其他项目的大卡 | A · 看板开发（小卡） | 其他项目的大卡 | 其他项目的大卡 |

其他项目的大卡按其真实阶段排列，表中第二行仅示意这些大卡仍可见。

首页大卡只突出项目名和子任务完成数。小卡正面突出任务名、运行或等你处理的状态，以及一句最新进展。任务说明、验收标准、聊天和资料放在详情中，保持首页紧凑。

大小卡都提供推进与回退操作。具体操作必须遵守下面的启动、验收及停止规则。

## 从项目目标到执行与验收

1. 用户写下项目目标，创建项目大卡。
2. AI 提出子任务方案，用户挑选、修改并确认后创建小卡。
3. AI 为小卡拟定验收标准，与任务说明一起保存；用户确认后才允许启动。
4. 小卡从待启动进入进行中时，直接将保存的任务说明、已确认的验收标准和必要项目资料发送给主聊天，让 Codex 开始执行，并打开该聊天。
5. 用户主要在主聊天跟进具体任务，需要整体查看时返回看板。看板同步显示真实执行状态及最新进展。
6. Codex 交付任务结果后，小卡自动进入待验收。交付判断应结合验收标准及成果；一次回复结束、等待澄清或执行失败均不能直接视为交付。
7. 用户验收通过后，小卡进入已结项。若需要修改，用户在卡片中填写意见，发送到原主聊天，小卡回到进行中继续执行。
8. 所有子任务结项后，大卡进入待验收；项目是否结项仍由用户确认。

首次执行需要建立并保存主聊天关联，后续推进或返工沿用该聊天。当前访谈确认的是这项产品行为，原生接口能否完整支持仍须核验。

## 阶段变化与父子联动

| 触发操作或事件 | 小卡变化 | 大卡变化 |
| --- | --- | --- |
| 小卡从灵感池推进到待启动 | 进入待启动，准备任务说明与验收标准 | 不自动启动项目 |
| 任一小卡开始执行 | 进入进行中，向主聊天发送任务并打开聊天 | 自动进入进行中 |
| Codex 交付某张小卡的结果 | 自动进入待验收 | 保持当前阶段 |
| 用户通过某张小卡的验收 | 进入已结项 | 当所有子任务均已结项时进入待验收 |
| 用户提出修改意见 | 意见发送到原主聊天，回到进行中 | 进入或保持进行中 |
| 用户回退一张正在执行的小卡 | 停止其当前执行，回到所选较早阶段；聊天和成果保留 | 不重置其他小卡 |
| 用户回退项目大卡 | 所属所有小卡停止执行并统一回到待启动，包括已结项、待验收及灵感池中的小卡；聊天和成果保留 | 回到用户选择的较早阶段 |
| 用户确认项目验收通过 | 保持各自状态 | 进入已结项 |

项目大卡回退是整个项目范围的阶段重置。即使大卡回到灵感池，其所属小卡仍统一回到待启动，这是用户明确指定的规则。它只重置阶段并停止执行，不删除聊天、已有成果或项目资料。

## 资料与原清单功能的归属

| 原清单中的能力 | 新版位置与用途 |
| --- | --- |
| 想法与待办记录 | 项目大卡与子任务小卡的灵感池、任务说明及推进操作 |
| 资料保存、AI 分类与总结 | 项目内资料；主要从主聊天提取精选成果、关键决定与可复用结论，附来源，用户可编辑或移除 |
| 检索与引用问答 | 围绕项目目标、子任务和资料查找并作答，引用能够追溯至来源 |
| 阶段总结与行动建议 | 项目内回顾，结合小卡推进情况、聊天成果和资料生成；新建议经用户确认后成为子任务 |
| 历史资料整理 | 用户选定一批已有聊天，AI 建议项目与子任务归属，用户确认后关联 |
| 模型、主题、存储与备份 | 作为设置及基础能力保留，首页聚焦任务看板 |

资料、问答和回顾集中在项目内。首页不另设全局收件箱或独立信息库。历史聊天整理仅处理用户选定的范围。

## 使用体验

- 采用紧凑工作台风格：中性灰、无衬线字体、清晰边界，突出阶段、执行状态和当前可用操作。
- 大卡负责总览，小卡负责执行；任务启动后直接进入主聊天，返回看板查看整体。
- 普通进展更新卡片；仅对等用户回复、执行失败、待验收等需要处理的情况提醒。
- 所有项目和小卡使用 `F:\workspace`。任务说明及项目资料明确具体工作范围。
- 每张小卡只有一个主聊天，可添加其他关联聊天；界面应明确主聊天身份，避免重复启动。

## 实现时采用的建议约定

下面是为使规则可执行而提出的设计约定，不是用户逐项选择的访谈结论：

- 任务说明或验收标准有实质修改时，重新确认当前版本后才启动。验收标准不变的返工直接发送修改意见。
- 大卡回退前展示所有受影响小卡及正在执行的数量，并提供一次明确的执行操作。
- 聊天发送、停止执行和阶段更新依据实际返回结果呈现。失败时显示原因，不用修改阶段来冒充已经启动或停止。
- 项目停止尚未完成时，不用“所有小卡待启动”掩盖仍在运行的小卡。旧执行后来返回的交付结果不覆盖已经回退后的阶段。
- 只有包含至少一张小卡的项目，才适用“所有小卡结项后自动进入待验收”。
- 大卡向前推进默认不隐含批量启动所有小卡；每张小卡按已确认说明单独启动。批量启动不纳入本轮核心流程。
- 已结项项目追加新任务时的重新打开方式，留待实现时补齐，不能默认套用会重置所有小卡的回退操作。

## 原生集成核验与交付边界

当前 0.1.0 已具备本地 MCP 插件、global/thread 入口注册、记录管理及预填聊天链接。第一版实际桌面侧栏显示和原生 AI 写回尚未实测；聊天链接也不等于直接启动执行。

下一版实现前需要核验：

| 需求 | 需确认的宿主能力 |
| --- | --- |
| 启动或继续某张小卡的主聊天 | 创建聊天、获取真实聊天引用、向指定聊天直接发送任务并导航过去 |
| 持续显示执行进展 | 读取真实运行状态、等待用户处理状态、错误与最新进展 |
| 自动送验 | 获得交付信号及成果信息，结合已确认验收标准判断，避免将普通回复结束当作完成 |
| 回退时停止执行 | 停止指定聊天的当前执行并取得停止确认；项目回退需要覆盖所有正在运行的小卡 |
| 历史聊天关联与资料沉淀 | 访问用户选定的历史聊天、保存来源引用、提取并写回精选资料 |

这些需求目前不能作为已经实现的功能展示。若宿主存在能力限制，应明确记录限制，再确定可用交互；不得用本地卡片状态模拟真实聊天执行。

## 减法审查

实际目标是「任务拆分 → 确认标准 → 执行 → 验收 → 项目沉淀」。本轮保留一张看板、两级卡片、小卡主聊天和项目资料即可服务这个目标。典型项目不超过 10 张小卡，无需分页、更多任务层级或独立项目看板。

沿用现有本地插件与存储，现阶段无需新增数据库、登录体系、公网托管或后台定时器。此次仅保存设计决定与更新文档引用，运行代码和安装版本仍为 0.1.0。
